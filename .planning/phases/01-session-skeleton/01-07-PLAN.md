## Gap Being Closed

From `01-VERIFICATION.md` `gaps:` (the only actionable input), status `partial`:

> "The Create button is disabled while a create request is in flight, so a double-click produces exactly one session" (01-03 plan truth, verification: backstop)

- **Root cause:** `app/ui/home_page.py` `create()` has no re-entrancy flag. `name_input.on("keydown.enter", create)` bypasses the button disable. On the success path, the cleanup `create_button.enable()` runs before `ui.navigate.to`.
- **Test gap:** `tests/ui/test_home.py` has no double-trigger test.
- **Missing:**
  - a re-entrancy flag that does not depend on the button and stays locked after a successful create;
  - a UI test that fires two `keydown.enter` events and two clicks against a slow fake repository and asserts `create_calls == 1`.
- **Fix shape:** REVIEW WR-01.

### Planner notes (verified on a scratch copy; the repo was not modified)

The tests in this plan were prototyped on a copy of `app/` and `tests/ui/` using the repo's own `.venv` (NiceGUI 3.18.0).

- **Why a double click gets through.** `UserInteraction.click()` skips disabled buttons. However, `events.handle_event` schedules an async handler as a background task. Two back-to-back `.click()` calls (no await between them) therefore both pass the enabled check before the first handler runs `create_button.disable()`. A double Enter goes through `trigger`, which never checks `enabled`. Only a flag that the handler checks itself closes both paths. A real browser double click or key-repeat Enter reaches the server as two events in the same way.
- **RED on HEAD:**
  - double Enter: `assert 2 == 1`
  - double click: `assert 2 == 1`
  - stays-locked-after-success: the button is enabled after a successful create
  - the failure-release, rejected-name and two-browser tests pass on HEAD (they are guards)
- **GREEN with the WR-01 shape:** 29/29 UI tests passed in 10 consecutive runs, and the quick suite reported 96 passed. `ruff check` and `ruff format --check` were clean on the three changed files. (Revision 1 re-ran the prototype with the sixth test, `test_rejected_name_releases_the_lock_for_a_retry`.)
- **Wrong fixes are caught:**
  - A module-level flag fails the two-browser test, and its lock state leaks into later tests.
  - Clearing the flag and re-enabling the button in a cleanup block that also runs on success fails the stays-locked test.
  - Keeping the `return` in the InvalidProjectName branch fails the rejected-name test. That branch skips the release, so the button stays disabled.
- **Simulation artifact.** `User.__getattribute__` rebinds the global `ui.navigate` to whichever simulated user was accessed last. In a two-user test, the canvas can open in the other simulated browser. The two-browser test therefore asserts call and row counts, never which browser lands where.

<objective>
Make session creation from the home page single-shot per browser tab (SESS-01). Enter and click are both guarded by one per-page `creating` flag:
- The flag is set before the first await.
- It stays set after a successful create, until the browser navigates away.
- It is cleared on every non-success outcome (a failed create or a server-side name rejection), so the user can retry.

Prove it with gated-fake UI tests for double Enter, double click, the success lock, the release after a failed or rejected create, and two browsers creating in parallel.

Purpose: close the single 01-VERIFICATION gap (REVIEW WR-01). The 01-03 backstop truth becomes explicit, test-backed truths, and the SESS-01 idempotency and concurrency edges are resolved.
Output: a hardened `app/ui/home_page.py`, a `create_gate` on `FakeRepository`, and six new tests in `tests/ui/test_home.py`.

CONTEXT.md decisions D-01 to D-04 (display-name prompt and rules) are not touched by this gap. They remain implemented and verified by 01-06.
</objective>
