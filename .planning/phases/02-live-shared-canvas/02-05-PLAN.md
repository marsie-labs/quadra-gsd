## Phase Goal

> ROADMAP Phase 2 Goal (verbatim): "Participants add cards to any quadrant, and every connected browser on the session sees them appear live, relayed by the Python server from Supabase Realtime."

Quoted verbatim; no user story is invented (see 02-01).

"Relayed by the Python server" is only as good as the server's own Realtime subscription. After this plan, a dropped or expired Realtime connection heals itself, and the canvases catch up on anything missed while it was down. A developer can see the recovery state at `/healthz`.

Phase 1 left this open on purpose:
- Pitfall 12: secret-key connections are capped at 24 h.
- Assumptions A7/A8: realtime-py's reconnect behavior was unverified.
- 01-04-SUMMARY: "Phase 2 must resync there".
- Review IN-03: a warn-mode failure is permanent.

## Flagged assumptions

- **realtime-py 2.33 reconnect behavior (verified by reading .venv source, not live):**
  - `_listen` only reconnects on `ConnectionClosedError`. A normal close (`ConnectionClosedOK`) ends the listen task silently, and the heartbeat swallows `ConnectionClosedOK`.
  - On its own reconnect, the library re-sends each channel's join, and the original subscribe callback fires SUBSCRIBED again (receive hooks persist on the join push).
  - The supervisor therefore relies on the private `AsyncRealtimeClient._listen_task`, pinned by uv.lock. A unit test asserts the attribute exists, so an upgrade that renames it fails loudly instead of silently disabling recovery.
- **SYNC-04 (edge probe: unclassified, left unresolved):** see 02-04; this plan covers the server-side half.
- **The live test forces the drop** by closing the hub's websocket from the client side (`_ws_connection.close()`, a normal close). That reproduces the "socket ended, library does not reconnect" path. The library's own error-reconnect path is covered offline by the re-join unit tests.

<objective>
Make the hub's Realtime subscription self-healing and make recovery visible: re-join and connection-loss handling, single-flight recovery with capped backoff, a supervisor for silently closed sockets, resync of every canvas after change data capture is re-proven, and README documentation for the whole phase.

Purpose: SYNC-04 on the server side, so SYNC-01/SYNC-02 keep holding past Realtime outages and the 24 h connection cap.
Output: the hub recovery machinery, offline recovery tests, the live dropped-socket test, README Phase 2 sections.
</objective>

realtime-py 2.33 facts (verified in .venv realtime/_async/client.py and channel.py):
- `AsyncRealtimeClient.__init__(url, token=..., auto_reconnect=True, max_retries=5, ...)`; `connect()` retries with backoff, then raises.
- `_listen()` reconnects only on `ConnectionClosedError`; a normal close ends the task. `_reconnect()` re-joins JOINED/JOINING channels, which re-fires the subscribe callback with SUBSCRIBED.
- `channel.subscribe(callback)` may be called once per channel instance; the callback receives `RealtimeSubscribeStates` SUBSCRIBED / CHANNEL_ERROR / TIMED_OUT / CLOSED.
