## Design decisions recorded here (Claude's discretion in CONTEXT.md)

- **updated_at maintenance: a DB trigger.** `cards_touch` runs BEFORE UPDATE for each row and sets `updated_at := greatest(pg_catalog.clock_timestamp(), old.updated_at + interval '1 microsecond')`. It covers direct DB edits (SYNC-03). Using the clock at trigger time, bounded below by the previous value plus one microsecond, makes updated_at strictly increase in commit order even when two writers race on one row (the BEFORE trigger sees the row version it locked), which the Phase 2 stale guard (older ignored, equal applies) depends on.
- **The "(edited)" signal (D-06): a nullable `text_updated_at timestamptz`.** Null means never edited, so existing rows need no backfill. The trigger owns it on UPDATE: the new updated_at when `new.text is distinct from old.text`, otherwise the old value (a writer cannot forge or clear it).
- **Write path: PostgREST `update` per operation, no RPC.** Each update filters `id`, `workspace_id` and `deleted_at is null` and returns the full row (PostgREST returns the representation by default). An empty result means the card is gone or belongs to another session: the service raises `CardGone`.
- **Projection: in place, with an optimistic overlay.** Today `_apply` deletes and rebuilds a card's widgets on every row. This plan changes CanvasView to keep the latest server row per card (`_cards`, stale guard unchanged) plus at most one optimistic row per card while that card's write is in flight (`_optimistic`). What is shown is the optimistic row if any, else the server row. `_render(card_id)` creates the card element once, then only updates label text in place and moves the element to its sorted position. Echoes and confirmations of the participant's own change therefore never rebuild or duplicate the card (CARD-08, Pitfall 5), and an open editor inside the card survives remote updates (needed by D-04 in 03-02).
- **Pending writes are not visually marked.** A write takes roughly 100-300 ms; a dim that appears and disappears that fast would itself read as flicker (SC-5). 03-02 disables the card's menu button while its write is in flight, which is the only cue.
- **A confirmation is applied only while the card is still known.** If a delete or a snapshot removed the card while its write was in flight, the removal stands. Realtime delivers in commit order, so only the HTTP response can arrive after a later delete event; this rule stops it from resurrecting the card.

## Flagged assumptions

- **Postgres row-lock behavior (trigger correctness under races):** the BEFORE UPDATE trigger runs after the row is locked and sees the latest committed version as OLD, so the `old.updated_at + 1 µs` floor orders racing writers. Task 2 proves the floor against an explicit older updated_at; a true race cannot be forced reliably from a test and is a backstop truth in 03-04's concurrent reorder proof.
- **Until the migration is pushed, every canvas page answers 503,** because list_cards now selects text_updated_at. Task 1 pushes before any live run, and the README tells developers to push migrations before starting the app.
