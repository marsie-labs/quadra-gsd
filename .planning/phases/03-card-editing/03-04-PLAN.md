## Phase Goal

> ROADMAP Phase 3 Goal (verbatim): "Participants can edit, delete, move and reorder cards collaboratively, and their own actions feel instant."

Quoted verbatim; no user story is invented (see 03-01).

This plan adds two slices on the 03-01 projection model (optimistic overlay, in-place `_render`, guarded `_write`):
- **Task 1, Delete:** instant, a toast, soft, idempotent, rolls back on failure.
- **Task 2, Move to:** the end of the chosen quadrant, instant, rolls back on failure.
- **Task 3:** proves both live against hosted Supabase, including two concurrent deletes and the database refusing a move into another session.

## Carried-forward decisions

- **D-05:** anyone on the link can delete or move any card; no display name needed; the author stays the creator.
- **D-07:** one menu per card in the order Edit, Move to, Move up, Move down, Delete. This plan adds Move to and Delete.
- **D-08:** Delete is instant, with no confirmation and no undo, the toast "Card deleted", and a soft delete.
- **D-09:** Move to places the card at the end of the target quadrant, following the add rule (`max_order_index` + `ORDER_GAP`).

## Design decisions recorded here (Claude's discretion)

- **delete_card returns the deleted row or None.** None means the card was already deleted or is not in this session; both are treated as success. Repeating a delete is harmless, and a racing second delete is not an error (CARD-03 idempotency).
- **The toast is shown with the optimistic removal**, not after the write: D-08 asks for instant feedback. A failed write then adds the failure message and brings the card back.
- **Move to is a submenu** ("Move to" item with a chevron and a nested menu), so the top-level menu keeps the D-07 shape. The item for the card's current quadrant is hidden, not removed, so the submenu needs no rebuild when the card moves. Choosing a quadrant also closes the top-level menu.

## Flagged assumptions

- **CARD-04 (edge probe: unclassified, left unresolved):** the probe could not classify this requirement into an edge category. Its behavior is covered by the move truths above (end-of-target placement, rollback, cross-session rejection, live propagation), not by an edge row.
- **Optimistic end position vs stored position:** the optimistic order_index uses the target's highest shown order_index + 1024, and the service recomputes it from the database. When someone adds to the target quadrant concurrently, the confirmed row may place the card one step differently; the confirmed row then repositions it once. This is the expected last-write-wins correction, not flicker.
